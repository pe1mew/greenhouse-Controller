# Greenhouse Controller — Claude project guide

Auto-loaded by Claude Code into every session in this repo. Keep terse; deeper material lives behind the pointer table below.

## Identity

ESP32-S3 firmware for a greenhouse ventilation controller. ESP-IDF 5.5 via PlatformIO (`framework=espidf`, `espressif32@6.12.0`). FreeRTOS task-graph design. Custom partition table (dual app banks + dual LittleFS + coredump). Dutch operator manuals (boer + beheerder).

Production deployment at Herenboeren Willemshoeve (Soest). **There are two hardware rigs, and the development rig takes a SWAPPABLE Lolin ESP32-S3 module** (corrected 2026-09-12):

- **Production rig** — at Herenboeren Willemshoeve (Soest), module **5C88**, ROTA `mainstream`. Remote, behind NAT, no push path.
- **Development rig** — SD and relays live, the M3 rope rig and the **real wire encoder at Modbus addr 40**, ROTA `soak`. **The T/RH (addr 1) and S200 wind (addr 44) slaves are EMULATED here** (operator, 2026-09-14; this line previously said "sensors live", which was wrong and had been shaping conclusions). **Consequence: any bus measurement taken on this rig for addr 1 or addr 44 characterises the emulator, not the field sensors** — so the 2026-09-14 response-latency figures (FG6485A ~22.5 ms, S200 ~63 ms median) are the emulator's, and do not transfer to 5C88 unexamined. It also *strengthens* the gh#66 master-side argument rather than weakening it: production's real sensors and the rig's emulated ones fail at comparable rates while being entirely different implementations, which points at the one thing they share. **`FDA4` and `2344` are modules, not separate units: they take turns in this one rig and inherit its hardware. Only one is fitted and powered at a time.**

**A dev module that does not answer is almost certainly the one not fitted — that is expected, not a crash.** Establish which module is in the rig before concluding a board has hung. **Swapping modules ends any soak**, and the SD card stays with the rig, so a swap splices two firmwares into one log file.

Addresses are fixed DHCP reservations: **`FDA4` is always `192.168.20.169`** and **`2344` is always `192.168.20.160`**, so the address identifies the module. ROTA config is per-module and an IO0 reset erases it. `devices.json` MAC keys and access routes live in user-global memory.

## Hard constraints

### Workflow (inherits from `~/.claude/CLAUDE.md`)

- **Never `git commit / push / merge / rebase / force-push`.** Stage changes and a suggested commit message; hand off to the user.
- **Commit to `main` directly** — no `claude/...` feature branches, no PRs unless explicitly requested.
- **Operator-commissioned branches are rare and short-lived:** `rota` (merged for 2.2.x) and `ropeSensor` (the M3 window-position sensor: T17, `drivers/windowPos/`, the `windowPos` IDF component, `SENSOR_HR ch3` / `ALARM ch6`), **fast-forwarded into `main` for 2.8.0 on 2026-09-17**. Integrate a branch by **rebasing it onto `main` and fast-forwarding**, never by merging `main` into it, and never put a commit on `main` that deletes the branch's files: either one makes git read the deletion as intentional and strips the work out of the branch. **The rebase method is worth reusing: start the replay from the branch's last OWN commit, not its tip.** Commits already cherry-picked to `main` in a better form otherwise replay against their own successors and fight them (`git checkout -b x-rebase <last-own-commit> && git rebase --empty=drop main`, verify, then `git branch -f <branch> x-rebase`). Work on a scratch branch so the branch is untouched until the build passes. **In the 2026-09-14 rebase every conflict was CLAUDE.md and none was contested**: both branches edit adjacent rows of the same table with no blank line between, so git marks the block; `python bin/resolve_md_rebase.py` takes whichever side changed each line and **refuses** if any line was changed by both. `git pull` after a rebase is the trap git itself suggests: it merges the pre-rebase history back and undoes the work.
- **Branch protection rejects merge commits on `main`** — if a branch must merge, rebase + fast-forward only.
- **No `--no-verify` / hook-skip / `--no-gpg-sign`.** Fix the hook, don't bypass it.
- **The hooks live in `.githooks/` and are OPT-IN per clone:** `git config core.hooksPath .githooks`. **They ARE enabled in this clone as of 2026-09-14** (verified: `core.hooksPath` is set) — they were not on 2026-09-12, so neither the gh#9 manifest-placeholder rule nor the gh#64 config check was running then; a hook that is not installed enforces nothing. **Re-check with `git config core.hooksPath` rather than trusting this line** — it is per-clone and this file cannot know. Note the hook runs on `cherry-pick` too, so a pick that lands a config key change is verified like any other commit.
- **Two copies of the WiFi credentials exist** (gh#56): the app's `wifi/ssid` + `wifi/psk`, and ESP-IDF's own `nvs.net80211` (because `esp_wifi_set_storage()` is never called, so `WIFI_STORAGE_FLASH` applies). Erasing only the app namespace leaves the unit reconnecting to the old network while logging *"no SSID in NVS"*. The IO0 level-2/3 reset now calls `nm_wifi_erase_persistent()` (2.4.8). **Anything that erases or provisions WiFi must handle both copies.**

### Web GUI

- **A control the operator cannot use right now is GREYED OUT, never hidden** (rule adopted 2026-09-16). Dim it, make it inert, and **say why next to it** — `.disabled-block` + `.disabled-why` in `style.css`; `commSetAvailable()` in `app.js` is the reference implementation, and `.rh-dep.rh-disabled` on the Humidity card is the older instance of the same idea. **Hiding answers no question.** An operator looking for a setting that is not on screen cannot tell *"this build does not have it"* from *"wrong tab"* from *"it is broken"*, and has nothing to search for or quote. That is not hypothetical: the entire **Linear control** group (window size, **deadzone**, calibration, teach) was `hidden` whenever `/api/diag/commission` did not answer, so when two routes silently failed to register the deadzone setting simply vanished and the operator had to ask where it had gone. **The reason goes ABOVE the greyed element, never inside it** (gh#74, fixed 2026-09-20): `opacity` applies to an element and its descendants as one group, so a reason inside a dimmed block is dimmed with it, and the CSS rule that claimed otherwise did nothing for a year. `#wpos-unfitted-why` above `#wpos-dep` and `#cm-unavailable` above `#cm-body` are the two instances. **Exception, narrow: content that does not exist at all** (a row with no data, a farmer-vs-admin surface) may be absent; a *feature that exists and is currently unavailable* may not.

### Releases & OTA

- **Paired-commit invariant.** Push firmware AND assets within 120 s of each other (`FW_DONE` fallback timer commits firmware alone after that, stranding the asset partition).
- **Verify post-OTA** by reading both `fw_ver` AND `asset_version` from `/api/status`. Neither alone is sufficient — a mismatch means the asset partition was left behind.
- **SemVer cadence:** feature releases bump minor (1.16.x → 1.17.0); patch is for bug-fix-only. Decide by asking: *did this add a user-visible feature, a new task, a new NVS namespace/key, or a payload-shape change?* If yes → minor, reset patch to 0. Don't let a run of patch-only commits pull the next bump into patch by inertia.
- **Greenfield flash uses `--flash_mode dio`** for the bootloader header byte. Runtime `board_build.flash_mode = qio` stays. Mixing them causes an `ets_loader.c` boot loop.
- **First flash on every new unit must erase the coredump partition** at `0x620000` (size `0x10000`). IDF reads garbage otherwise and panics on every subsequent boot.

### Honesty

- Never claim firmware was tested without a real hardware run (or soak data confirming the change held under load).
- Never claim "OTA succeeded" without a post-reboot `/api/status` query confirming both `fw_ver` and `asset_version` match.
- Never claim "no SD log gaps" without actually parsing timestamps — the HEAD endpoint is broken (see gotcha log).
- When something cannot be verified in this environment, say so explicitly.

| Touching the Modbus/RS485 bus (driver, or any new caller) | The driver **does** hold a bus mutex since gh#49, but **single-caller is still policy**: ~215 ms of blocking must stay out of T2/T3. The receive loop **never yields**, so a back-to-back poller starves the idle task and trips the 5 s TWDT. `modbus_init()` deletes and reinstalls the UART, so a re-init during another task's transaction is a use-after-delete (gh#69, two boot panics); it takes the bus mutex now. **The mutex serialises ACCESS but not the SILENCE the RTU protocol needs between frames** — `MODBUS_IFG_US` is 20 000 us and is **paid before `bus_unlock()`**, so the lock means "the bus is yours AND idle"; a slave that reads a request as a continuation of the previous frame answers with **zero bytes and a timeout, never a CRC error**. ## Release cycle

1. Edit code; bump `-DFIRMWARE_VERSION=\"X.Y.Z\"` in `firmware/platformio.ini`
2. `powershell -ExecutionPolicy Bypass -File bin/build_release.ps1`
3. New `## [X.Y.Z]` section at top of `changelog.md`; write `bin/X.Y.Z/release-notes.md` (use prior release's structure)
4. Hand off staged changes for the user to commit
5. OTA push to soak **FDA4**: `python bin/ota_push.py bin/X.Y.Z/greenhouse-controller-X.Y.Z.bin` (FDA4 `192.168.20.169` is now the default host)
6. Verify both `fw_ver` and `asset_version` from `/api/status`
7. Soak ≥ overnight (or longer for high-risk changes)
8. Production (5C88) only after soak passes. 5C88 now pulls via **ROTA** on the `mainstream` channel — `python bin/rota_release.py promote <ver>` (or hand-edit `channels/mainstream.json`) and it applies in its own night window, **no site visit** (this is what ROTA added, per [design/remoteOTAstudy.md](design/remoteOTAstudy.md)). 5C88 is still behind NAT/outbound-only, so there is no *push* path — but the ROTA *pull* path now covers routine production updates.
