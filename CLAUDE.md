# Greenhouse Controller — Claude project guide

Auto-loaded by Claude Code into every session in this repo. Keep terse; deeper material lives behind the pointer table below.

## Identity

ESP32-S3 firmware for a greenhouse ventilation controller. ESP-IDF 5.5 via PlatformIO (`framework=espidf`, `espressif32@6.12.0`). FreeRTOS task-graph design. Custom partition table (dual app banks + dual LittleFS + coredump). Dutch operator manuals (boer + beheerder).

Production deployment at Herenboeren Willemshoeve (Soest). **There are two hardware rigs, and the development rig takes a SWAPPABLE Lolin ESP32-S3 module** (corrected 2026-09-12):

- **Production rig** — at Herenboeren Willemshoeve (Soest), module **5C88**, ROTA `mainstream`. Remote, behind NAT, no push path.
- **Development rig** — SD and relays live, the M3 rope rig and the **real wire encoder at Modbus addr 40**, ROTA `soak`. **The T/RH (addr 1) and S200 wind (addr 44) slaves are EMULATED here** (operator, 2026-09-14; this line previously said "sensors live", which was wrong and had been shaping conclusions). **Consequence: any bus measurement taken on this rig for addr 1 or addr 44 characterises the emulator, not the field sensors** — so the 2026-09-14 response-latency figures (FG6485A ~22.5 ms, S200 ~63 ms median) are the emulator's, and do not transfer to 5C88 unexamined. It also *strengthens* the gh#66 master-side argument rather than weakening it: production's real sensors and the rig's emulated ones fail at comparable rates while being entirely different implementations, which points at the one thing they share. **`FDA4` and `2344` are modules, not separate units: they take turns in this one rig and inherit its hardware. Only one is fitted and powered at a time.**

**A dev module that does not answer is almost certainly the one not fitted — that is expected, not a crash.** Establish which module is in the rig before concluding a board has hung. **Swapping modules ends any soak**, and the SD card stays with the rig, so a swap splices two firmwares into one log file.

Addresses are fixed DHCP reservations: **`FDA4` is always `192.168.20.169`** and **`2344` is always `192.168.20.160`**, so the address identifies the module. ROTA config is per-module and an IO0 reset erases it. `devices.json` MAC keys and access routes live in user-global memory.

## Hard constraints

### Workflow (inherits from `~/.claude/CLAUDE.md`)

- **Never `git commit / push / merge / rebase / force-push`.** Stage changes and a suggested commit message; hand off to the user.
- **Commit to `main` directly** — no `claude/...` feature branches, no PRs unless explicitly requested.
- **One operator-commissioned branch is active: `ropeSensor`** (since 2026-09-11, the second ever after `rota`). **All M3 window-position-sensor work lives there** — task T17 (`firmware/src/window_pos/`), the wire-encoder driver (`drivers/windowPos/`), the `windowPos` IDF component, the `SENSOR_HR ch3` / `ALARM ch6` log encodings and their `logparser.py` / `plot_daily.py` support. `main` ships the controller **without** any of it and must stay that way until the sensor work integrates. Integrate by **rebasing `ropeSensor` onto `main`**, never by merging `main` into it — and never put a commit on `main` that deletes the sensor files, because either one makes git read the deletion as intentional and strips T17 out of `ropeSensor`. **Rebased 2026-09-14 and the method is worth reusing: start the replay from the last SENSOR commit, not the branch tip** — commits already cherry-picked to `main` in a better form otherwise replay against their own successors and fight them (`git checkout -b rope-rebase <last-sensor-commit> && git rebase --empty=drop main`, verify, then `git branch -f ropeSensor rope-rebase`). Work on a scratch branch so `ropeSensor` is untouched until the build passes. **Every conflict was CLAUDE.md and none was contested** — both branches edit adjacent rows of the same table with no blank line between, so git marks the block; `python bin/resolve_md_rebase.py` takes whichever side changed each line and **refuses** if any line was changed by both. `git pull` after a rebase is the trap git itself suggests: it merges the pre-rebase history back and undoes the work.
- **Branch protection rejects merge commits on `main`** — if a branch must merge, rebase + fast-forward only.
- **No `--no-verify` / hook-skip / `--no-gpg-sign`.** Fix the hook, don't bypass it.
- **The hooks live in `.githooks/` and are OPT-IN per clone:** `git config core.hooksPath .githooks`. **They ARE enabled in this clone as of 2026-09-14** (verified: `core.hooksPath` is set) — they were not on 2026-09-12, so neither the gh#9 manifest-placeholder rule nor the gh#64 config check was running then; a hook that is not installed enforces nothing. **Re-check with `git config core.hooksPath` rather than trusting this line** — it is per-clone and this file cannot know. Note the hook runs on `cherry-pick` too, so a pick that lands a config key change is verified like any other commit.
- **Two copies of the WiFi credentials exist** (gh#56): the app's `wifi/ssid` + `wifi/psk`, and ESP-IDF's own `nvs.net80211` (because `esp_wifi_set_storage()` is never called, so `WIFI_STORAGE_FLASH` applies). Erasing only the app namespace leaves the unit reconnecting to the old network while logging *"no SSID in NVS"*. The IO0 level-2/3 reset now calls `nm_wifi_erase_persistent()` (2.4.8). **Anything that erases or provisions WiFi must handle both copies.**

### Web GUI

- **A control the operator cannot use right now is GREYED OUT, never hidden** (rule adopted 2026-09-16). Dim it, make it inert, and **say why next to it** — `.disabled-block` + `.disabled-why` in `style.css`; `commSetAvailable()` in `app.js` is the reference implementation, and `.rh-dep.rh-disabled` on the Humidity card is the older instance of the same idea. **Hiding answers no question.** An operator looking for a setting that is not on screen cannot tell *"this build does not have it"* from *"wrong tab"* from *"it is broken"*, and has nothing to search for or quote. That is not hypothetical: the entire **Linear control** group (window size, **deadzone**, calibration, teach) was `hidden` whenever `/api/diag/commission` did not answer, so when two routes silently failed to register the deadzone setting simply vanished and the operator had to ask where it had gone. The reason text stays at full opacity and stays clickable while the block it explains is inert — it is the one thing the operator needs to act on. **Exception, narrow: content that does not exist at all** (a row with no data, a farmer-vs-admin surface) may be absent; a *feature that exists and is currently unavailable* may not.

### Releases & OTA

- **Paired-commit invariant.** Push firmware AND assets within 120 s of each other (`FW_DONE` fallback timer commits firmware alone after that, stranding the asset partition).
- **Verify post-OTA** by reading both `fw_ver` AND `asset_version` from `/api/status`. Neither alone is sufficient — a mismatch means the asset partition was left behind.
- **SemVer cadence:** feature releases bump minor (1.16.x → 1.17.0); patch is for bug-fix-only. Decide by asking: *did this add a user-visible feature, a new task, a new NVS namespace/key, or a payload-shape change?* If yes → minor, reset patch to 0. Don't let a run of patch-only commits pull the next bump into patch by inertia.
- **Greenfield flash uses `--flash_mode dio`** for the bootloader header byte. Runtime `board_build.flash_mode = qio` stays. Mixing them causes an `ets_loader.c` boot loop.
- **First flash on every new unit must erase the coredump partition** at `0x620000` (size `0x10000`). IDF reads garbage otherwise and panics on every subsequent boot.

### Honesty

- Never claim firmware was tested without a real hardware run (or soak data confirming the change held under load).
- Never claim "OTA succeeded" without a post-reboot `/api/status` query confirming both `fw_ver` and `asset_version` match.
- Never claim "no SD log gaps" without actually parsing timestamps — the HEAD endpoint is broken (see gotcha log).
- When something cannot be verified in this environment, say so explicitly.

Known limitation: a genuinely closed window with a faulty end sensor trips it.** **§12.4 rule 1 "moving means moving" LANDED 2026-09-15** as `LOG_PARAM_WPOS_STALL` = 249 plus a `stall_faults` counter: while the relay is energised the measured rate must reach half nominal within `min(5 s, travel/2)`, or the leaf is not following the motor. **It is the only detector for a shorted wiper**, which reports a plausible CONSTANT position that leaves every device status bit clear (bit 6 is inert here for lack of electrical headroom). It **reports and does not act** — nothing consumes position yet, so the response belongs with the T2 change. Two guards are load-bearing: only *accepted* samples count as movement evidence, and at least one accepted sample is required, so an encoder that goes absent mid-stroke stays `WPOS_GATE_NO_SENSOR` instead of being misreported as a stall. **A third was added 2026-09-16 after the first soak FAILED on it:** a stroke driven toward the end the leaf is *already* at cannot move — the end switch cuts the drive — so rule 1 **exempts** it (`at_end_exempt` counter) when bit 3 stays made **and** position stays within `deadzone_m3` of the TARGET end **on every sample of the grace window**. Without it rule 1 false-tripped on every CLOSE_ALL of a closed M3: each boot, **twice per OTA push**, and each LCD logout. **Continuity is the safety property, not either condition alone** — a shorted wiper reads a constant 0, so an OPEN window starts a CLOSE at "0, bit 3 made" (the open end sensor), and only bit 3 *dropping* as the leaf leaves that end keeps the fault judged. T2's belief cannot substitute: it is `WIN_UNKNOWN` after a reboot, exactly for the stroke that needs the exemption. **Soaks count JUDGED strokes** (`strokes - at_end_exempt`), or a soak of recalibrations passes on strokes rule 1 never looked at. `logparser.py` and `plot_daily.py` decode them, and **`logparser.md` now does too (since doc 1.12), including `LOG_PARAM_WPOS_MODE` = 248 and the T5 fault-reason byte in `ALARM ch = 4/5` `value_b`.** Sensor at Modbus **address 40**, calibrated `40004`=15000 / `40005`=0 / `40006`=858. **Read plan §2a before touching any of it** — the switch/limit/overlap geometry is not what the earlier drafts assumed. **The sensor-presence gate LANDED 2026-09-12** (the three startup branches used to log and fall through — "T17 idle" did not idle and "REFUSING" did not refuse). It publishes the control law via `windowpos_task_ctrl_mode()`: **POSITION with a trusted sensor, TIMED fallback without one** (operator decision). Demotion is immediate, promotion only at a stroke boundary; a shut gate re-probes every 30 s; BENCH build is a permanent latch; `WINDOWPOS_ERR_BUSY` never counts as a failure. AT-WP06 **failed first and found a real defect** — the idle read swallowed failures, so the gate was blind while M3 was at rest — then passed, with recovery measured at 31 s against `PROBE_RETRY_MS` = 30 s. **Still true: `ropeSensor` must not reach 5C88 until the sensor work integrates.** **The teach drives BOTH end sensors, from anywhere (2026-09-16):** a capture needs an end-sensor *make* after arming, so one traverse from a parked end never commits — the first teach only "worked" because T6 finished it. `bin/at_wp_teach.py` proves both ends; T17 aborts any armed teach the commissioning path does not own (param 245 value 4, `orphan_aborts`). **A teach and the LCD manual menu HOLD STANDBY until their admin session ends** (not persisted; gh#65): `bin/at_wp_teach_standby.py`, `bin/at_lcd_standby.py`. **Plan:** [design/integrateWindowPositionSensor.md](design/integrateWindowPositionSensor.md) — phases 0-4, Phase 5 out of scope. **Study:** [design/windowPositionSensorRequirements.MD](design/windowPositionSensorRequirements.MD) — M3 is a 40 m hanging flap on ropes (§1.4); absolute + >=1 Hz + measured at the flap are the requirements that decide a purchase; a threshold interrupt is ruled out on this PCB. **§12** evaluates the wire-encoder Modbus interface, contract v1.2, copied to [design/modbusInterfaceContractSpecification.md](design/modbusInterfaceContractSpecification.md): fit for purpose; the IP50 draw-wire unit is the procurement blocker; controller-side rules in §12.4. **Rebase guidance:** [design/rebaseRopeSensorOntoMain.md](design/rebaseRopeSensorOntoMain.md) |

## Release cycle

1. Edit code; bump `-DFIRMWARE_VERSION=\"X.Y.Z\"` in `firmware/platformio.ini`
2. `powershell -ExecutionPolicy Bypass -File bin/build_release.ps1`
3. New `## [X.Y.Z]` section at top of `changelog.md`; write `bin/X.Y.Z/release-notes.md` (use prior release's structure)
4. Hand off staged changes for the user to commit
5. OTA push to soak **FDA4**: `python bin/ota_push.py bin/X.Y.Z/greenhouse-controller-X.Y.Z.bin` (FDA4 `192.168.20.169` is now the default host)
6. Verify both `fw_ver` and `asset_version` from `/api/status`
7. Soak ≥ overnight (or longer for high-risk changes)
8. Production (5C88) only after soak passes. 5C88 now pulls via **ROTA** on the `mainstream` channel — `python bin/rota_release.py promote <ver>` (or hand-edit `channels/mainstream.json`) and it applies in its own night window, **no site visit** (this is what ROTA added, per [design/remoteOTAstudy.md](design/remoteOTAstudy.md)). 5C88 is still behind NAT/outbound-only, so there is no *push* path — but the ROTA *pull* path now covers routine production updates.
